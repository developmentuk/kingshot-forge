# Release 0.8.0 platform UI/UX audit

## Audit basis

This audit is based on the Release 0.8.0 branch at production merge commit
`9bd97dcdebded96bee4ac40f8888f0bcc5724173`. It is a static implementation
audit of the route registry, `AppLayout`, `AccountMenu`, `RoleContext`,
`ProtectedRoute`, the Admin feature pages and the existing responsive CSS.
Authenticated browser and Supabase-backed mutation checks remain validation
work, not assumptions made by this document.

The current mobile bottom navigation is a second, hard-coded navigation model
containing Home, Player Lookup, KvK Tracker, Gift Codes, My Forge and Personal
Progression. It is useful for players but must be derived from the same registry
as the desktop Player View menu.

## Audience and role findings

Signed-out users can see public Forge tools and updates. A normal signed-in
player receives the same player navigation plus account controls. Contributor,
creator and moderator experiences are not distinct workspaces: only selected
Admin links are conditionally appended to the Player sidebar. Admin and Owner
users receive the same mixed shell, with individual permission filters. The
implementation does not currently model Creator as a separate UI audience.

The UI role model supports `owner`, `admin`, `moderator`, `content_creator`,
`beta_tester`, `contributor` and `viewer`; the requested `player` label is a
default experience rather than a stored role. The current client uses
`maybeSingle()` for roles, so multiple roles are not safely represented.

## Completion and duplication findings

The Player Identity and My Forge routes are an established player-facing
vertical slice and should remain intact. Verification, editorial dataset
editing, Community Art moderation and Gift Redemption operations have real
loading/error/empty or mutation paths, subject to the Admin inventory. Import,
history, search and publish are visibly placeholder shells. The current Admin
dashboard mixes metrics/cards with links to those unfinished tools.

There are three navigation sources: desktop groups, Admin groups and mobile
bottom links. Labels also vary between `Publish` and `Publish Centre`, and
`Dashboard` is ambiguous between Player View and Admin. The Admin menu is
duplicated into the Player shell rather than selected through a workspace.

## Mobile and accessibility findings

The existing drawer, backdrop, Escape handling, `aria-expanded` and visible
focus styling are useful foundations. The long desktop sidebar and duplicated
mobile menu increase cognitive load and maintenance risk. Internal tables and
filter bars require route-by-route checks at 390px and 768px. Workspace choice
must be available from the account/header control on mobile, with a keyboard
reachable focus state and a clear current-workspace announcement. Status and
permission states must continue to use text as well as colour.

## Priority recommendations

1. Create one typed navigation registry with workspace, permission, status and
   audience metadata.
2. Add a role-aware workspace switcher; default to Player View and never use a
   stored preference as authorization.
3. Move internal links into Operations, Contributor/Creator and Moderation
   shells, retaining existing route implementations during migration.
4. Add server-authorized User Management and role mutation endpoints before
   exposing management controls.
5. Label or remove placeholder Admin routes from operational dashboard cards.
6. Protect `/admin/player-identity` consistently and test direct URL access.
7. Validate the resulting shells at 390px, 768px, 1024px and 1440px with
   keyboard and authenticated role fixtures.
