# Release 0.7.5 Auto Redeem gap analysis

Status: ready for Clark’s final production validation. The provider remains disabled and no new provider redemption was performed during this repair.

## Reference comparison

The donated KVK Planner was inspected at the approved local reference checkout. Its planner is useful for product and operations concepts: a code catalogue, pending/valid/invalid lifecycle, per-code and per-player outcomes, recheck actions, history, filtering and admin metrics. Its low-level provider implementation contains embedded signing and feed credentials, shared-session handling and a continuous daemon model. Those implementation details are not copied into Forge.

## Root cause of the hidden control

The Gift Centre wrapped the complete Auto Redeem block in `user && context`. `context` is populated by a separate `/api/giftcodes?action=context` request. A provider-disabled response, transient API failure or loading interval therefore made the condition false and removed the panel itself. Provider configuration, health gating and eligibility were not the cause of the disappearance; they were only evaluated inside the unreachable branch. The repair renders the user-facing block after authentication and uses a disabled fallback while context is unresolved or unavailable. Server-side `redeemAvailable` still rechecks provider health, configuration, verification, consent and active codes.

## Lifecycle, retry and governance decisions

Release 0.7.5 treats the existing Gift Codes Edge Function as the canonical discovered/active source. The current projection does not expose editorial approval, withdrawn or expired records to the browser, so those filters and manual code entry remain future catalogue work. A provider response is classified as success, already claimed, expired, invalid code/player, ambiguous external request, or retryable provider failure. Player-specific failure never globally invalidates a code.

Retries must create another attempt, preserve the original request lineage, require an active approved code, active consent, current verified linkage, no duplicate request, retry budget and a healthy provider. Conclusive outcomes are not retried. Admin requeue is intentionally deferred until the audit and lineage mutation are implemented together.

## Security and donated patterns rejected

Forge keeps signing material, cookies, provider bodies and credentials server-only. It does not redeem for arbitrary Player IDs, use proxy accounts, mutate verification/provider state from the browser, run continuous in-process daemons, delete redemption history, accept client-controlled results, or activate the donated external feed. The planner informed the catalogue and reporting vocabulary; its embedded credentials, bulk proxy-governor workflow, destructive recheck semantics and continuous loops were rejected.

## Release validation boundary

`KINGSHOT_REDEMPTION_ENABLED=false` remains required. The provider health row remains paused/open. This repair performs no provider redemption, does not weaken gating, and does not add a second redemption path. Responsive visual verification and a masked Admin drill-down remain follow-up validation for the next operational milestone; the current catalogue avoids full Player IDs and raw provider details.

## Preview API diagnosis

The deployed schema was checked directly: the provider-health, request and attempt tables and the required columns were present, the provider row was paused/open, and the existing RLS/service-role boundary remained intact. The Admin failure was at the aggregation boundary rather than a missing migration: catalogue retrieval coupled the external active-code feed, provider health and request history in one `Promise.all`, and the page then treated the result as an all-or-nothing dependency. A failure in any one operation produced the generic provider-status fallback and hid the catalogue and metrics. The repair exposes separate `operations`, `catalogue` and `metrics` requests and keeps each panel independently renderable with safe JSON errors.
