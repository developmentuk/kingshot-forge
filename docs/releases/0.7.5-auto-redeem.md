# Release 0.7.5 — Auto Redeem

## Player and Admin visibility repair

The Auto Redeem panel is a persistent part of the Gift Centre for authenticated users. Loading, provider-disabled, paused, circuit-open and service-error states render a clear disabled explanation while the official manual redemption fallback remains available. The server still rejects redemption unless configuration, provider health, verified linked-player state, consent and active codes all pass.

Admins can inspect the canonical active-code catalogue and aggregate request outcomes at `/admin/gift-redemption`. The view is intentionally aggregate-only: player history remains private, and editorial code approval, expiry history, drill-down and safe audited requeue are follow-up capabilities rather than implicit provider permissions.

## Preview operations polish

The Gift Centre formats provider state as human-readable status text and changes the disabled action copy for unavailable, paused, consent and running states. The trust copy confirms Kingshot player-service verification without claiming official Century Games account authentication or password verification.

Admin operations are loaded as independent provider-summary, catalogue and metrics requests. A failure in one panel no longer removes the others. The page exposes environment configuration, the environment kill switch, admin gate, circuit and health state, safe aggregate counts, mobile-safe filters and a horizontally scrollable catalogue. With `KINGSHOT_REDEMPTION_ENABLED=false`, the enable control cannot override the environment flag.

The preview runtime issue was resolved by replacing the Node-incompatible `AbortSignal.timeout()` call with a portable `AbortController` timeout. Admin responses remain JSON-only on the server, while the client validates content type before parsing.

## User outcome

Signed-in players with a verified linked Governor can grant explicit, revocable consent and start a user-triggered run against active Gift Codes. Forge processes codes sequentially, persists safe per-code outcomes and keeps manual copying available.

## Player verification trust model

Forge verifies that a Player ID is valid through the Kingshot player service and links it to the authenticated Forge account. Forge does not request a game password or claim official account authentication. A successful server-controlled link records `verification_status=verified`, `verification_method=kingshot_player_lookup` and a server-generated verification timestamp. Consent remains separate, and provider pause remains separate.

Legacy linked records are revalidated individually through the same trusted server path; they are not bulk-marked verified.

## Provider boundary

The server adapter follows the observed Kingshot flow: a signed player lookup followed by a signed gift-code request in the same short-lived session. Signing configuration, URLs, cookies and provider responses never reach the browser. The adapter uses bounded timeouts, no permanent-failure retries and sanitized result classifications.

The observed reference maps success, already claimed, expiry, invalid code/player, retryable timeout/network results and unknown responses into Forge-safe outcomes. CAPTCHA or anti-bot challenges are a hard stop; Forge does not bypass them.

## Consent and eligibility

Consent is recorded server-side for one verified linked `player_accounts` row, is versioned and revocable, and is never inferred from page visits. Forge does not request or store a game password. The server derives user and player ownership from the authenticated session.

## Persistence and RLS

The Gift Redemption foundation migration, the 0.7.5 corrective run/snapshot migration, the verification-column protection migration, the lookup-verification contract migration and the browser-insert correction migration are applied to the configured Supabase project. Consent, requests, attempts, audit events, provider health and runs are owner-readable; mutations and provider outcomes remain service-role/server controlled. A unique active-run index prevents concurrent runs for one player. The provider-health gate must be explicitly closed by an administrator before provider calls are allowed.

## Code provenance

The player page continues to use the existing `kingshot-gift-codes` adapter. Auto Redeem accepts only currently active records returned by that adapter and retains the temporary community-feed provenance limitation. No second gift-code registry was introduced.

## Configuration

Server-only variables are documented in `.env.example`: `KINGSHOT_REDEMPTION_PLAYER_URL`, `KINGSHOT_REDEMPTION_CODE_URL`, `KINGSHOT_REDEMPTION_SIGNING_KEY`, `KINGSHOT_REDEMPTION_ENABLED` and `KINGSHOT_REDEMPTION_TIMEOUT_MS`. Real values must be provided through the deployment secret manager and are never committed.

Production also requires the existing server Supabase variables `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` (the legacy `SUPABASE_SERVICE_ROLE_KEY` is accepted only for compatibility). The browser build separately requires `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`; no secret or signing variable may use a `VITE_` prefix. Initial production configuration must set `KINGSHOT_REDEMPTION_ENABLED=false`. The database provider-health row is an independent operational gate and must remain paused until post-deployment smoke checks pass.
