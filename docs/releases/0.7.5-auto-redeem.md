# Release 0.7.5 — Auto Redeem

## Status

In development. Controlled provider validation completed locally; production deployment remains out of scope for this task.

## User outcome

Signed-in players with a verified linked Governor can grant explicit, revocable consent and start a user-triggered run against active Gift Codes. Forge processes codes sequentially, persists safe per-code outcomes and keeps manual copying available.

## Player verification trust model

Forge verifies that a Player ID is valid through the Kingshot player service and links it to the authenticated Forge account. Forge does not request a game password or claim official account authentication. A successful server-controlled link records `verification_status=verified`, `verification_method=kingshot_player_lookup` and a server-generated verification timestamp. Consent remains separate, and provider pause remains separate.

Legacy linked records are revalidated individually through the same trusted server path; they are not bulk-marked verified.

## Provider boundary

The server adapter follows the observed Kingshot flow: a signed player lookup followed by a signed gift-code request in the same short-lived session. Signing configuration, URLs, cookies and provider responses never reach the browser. The adapter uses bounded timeouts, no permanent-failure retries and sanitized result classifications.

The observed reference maps success, already claimed, expiry, invalid code/player, retryable timeout/network results and unknown responses into Forge-safe outcomes. CAPTCHA or anti-bot challenges are a hard stop; Forge does not bypass them.

## Consent and eligibility

Consent is recorded server-side for one verified linked `player_accounts` row, is versioned and revocable, and is never inferred from page visits. Forge does not request or store a game password. The server derives user and player ownership from the authenticated session.

## Persistence and RLS

The Gift Redemption foundation migration and the 0.7.5 corrective run/snapshot migration are applied to the configured Supabase project. Consent, requests, attempts, audit events, provider health and runs are owner-readable; mutations and provider outcomes remain service-role/server controlled. A unique active-run index prevents concurrent runs for one player. The provider-health gate must be explicitly closed by an administrator before provider calls are allowed.

## Code provenance

The player page continues to use the existing `kingshot-gift-codes` adapter. Auto Redeem accepts only currently active records returned by that adapter and retains the temporary community-feed provenance limitation. No second gift-code registry was introduced.

## Configuration

Server-only variables are documented in `.env.example`: `KINGSHOT_REDEMPTION_PLAYER_URL`, `KINGSHOT_REDEMPTION_CODE_URL`, `KINGSHOT_REDEMPTION_SIGNING_KEY`, `KINGSHOT_REDEMPTION_ENABLED` and `KINGSHOT_REDEMPTION_TIMEOUT_MS`. Real values must be provided through the deployment secret manager and are never committed.

## Controlled validation status

Fixtures and local checks cover signing, provider normalization, consent, ownership, idempotency and safe persistence. The paused gate rejected eligibility before any run/request/attempt was created. After the administrator gate was enabled, the server-only controlled validation path submitted `HAPPYEMOJIDAY` and recorded the provider-safe `already_claimed` result; `Kingshot888` was not selected. A repeat request produced no provider result because the idempotency identity was already handled. This is a local controlled validation result, not a production deployment claim.
