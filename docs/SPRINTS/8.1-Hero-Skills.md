# Sprint 8.1 — Hero Skills

## Release

Release 0.6.0 — Hero Domain Complete

## Sprint objective

Deliver Hero Skills as the first complete post-Foundation canonical vertical slice using the existing Forge dataset, editorial, permission, publication and public-consumption platform.

Architectural rule: **Publish once. Consume everywhere.**

## Discovery summary

### Existing canonical Hero domain

The `heroes` table and live Heroes dataset currently provide canonical identity, classification, ratings, availability, descriptive content, portrait and provenance fields.

The public Hero Companion consumes active published Hero records through `getHeroCatalogue()` and now renders Hero Skills from the published canonical projection.

The Heroes Record Editor schema is connected to the existing editorial lifecycle and supports immutable versions, review, approval, queue-based publication, history, comparison, archive, restore and rollback.

### Existing Hero Skill persistence foundation

Supabase contains a `hero_skills` table linked to `heroes` through `hero_id`.

Its canonical fields include:

- stable editorial key;
- Hero relationship;
- name;
- category (`conquest`, `expedition`, `talent`, `exclusive_gear`);
- skill type;
- description;
- icon URL;
- display order;
- slot index;
- maximum level;
- active state;
- provenance and confidence;
- published editorial version metadata.

The table is the live persistence projection. Draft and workflow state remain in the existing editorial tables.

### Existing player-owned progression

`player_heroes` stores player-specific progression, including hero level, stars, power and legacy numbered skill-level fields.

Supabase also contains a relational `player_hero_skills` table that links a player's Hero to a canonical `hero_skills` record and stores `skill_level`.

Those structures describe a player's ownership and progression. They are not the canonical source for skill identity, names, descriptions, categories, ordering or provenance.

## Architectural decision

Hero Skills remain independent canonical records linked to Heroes.

The cross-layer dataset and editorial contract uses stable Hero slugs. The live publication projection resolves the Hero slug to the existing `heroes.id` foreign key when writing `hero_skills`.

This preserves clear ownership:

- `heroes`: canonical Hero identity and overview;
- `hero_skills`: published canonical skill definitions;
- `player_hero_skills`: player-owned skill progression;
- editorial platform: draft, review, approval, publication, history and rollback;
- Hero Companion: read-only consumer of published canonical content.

No replacement table or parallel Hero-specific publishing system was introduced.

## Canonical record model

The Hero Skill contract requires:

- stable skill ID for editorial and dataset use;
- stable Hero slug relationship;
- skill name;
- existing category vocabulary;
- optional skill type and description;
- optional icon URL;
- deterministic positive slot index;
- deterministic positive display order;
- positive maximum level;
- active state;
- provenance, verification and confidence metadata.

Slot indexes and display orders are unique within an active Hero. Missing or uncertain facts remain nullable and must not be invented.

## Deliberate boundaries

Sprint 8.1 does not include:

- player skill-level redesign or legacy-column migration;
- Widgets, Gear, Awakening, pairings or formations;
- localisation infrastructure;
- a replacement Hero Skill table;
- a new editorial architecture;
- automatically invented skill data;
- direct public reads from editorial draft tables.

## Publication and public projection

Publication uses the existing queue executor. The approved immutable version is projected to `public.hero_skills` before the editorial state is marked Published.

The live row records its published version ID, version number, publisher and timestamp. Repeated publication uses the stable editorial key and updates the same live row.

`public.published_hero_skills` is a `security_invoker` view. Its underlying RLS policy exposes only active rows with a published version ID. The Hero Companion and canonical Hero Skills loader read this projection rather than editorial drafts.

## Sprint 9.3 compatibility note

The Sprint 8.1 implementation is now treated as a legacy vertical-slice foundation, not proof of a complete trustworthy Hero Skills dataset. The 17 July 2026 read-only audit found zero canonical/editorial/published Hero Skill records, incomplete and unapproved staged evidence, no structured progression/unlock persistence, an incompatible slot constraint, and an overlapping permissive base-table SELECT policy.

Sprint 9.3 therefore defines a governed target contract and unapplied schema proposal. Earlier checked acceptance criteria remain historical test claims and must not be used to claim current live readiness until source approval, migration/publication compatibility and live validation are completed.
