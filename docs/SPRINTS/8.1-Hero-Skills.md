# Sprint 8.1 — Hero Skills

## Release

Release 0.6.0 — Hero Domain Complete

## Sprint objective

Deliver Hero Skills as the first complete post-Foundation canonical vertical slice using the existing Forge dataset, editorial, permission, publication and public-consumption platform.

Architectural rule: **Publish once. Consume everywhere.**

## Discovery summary

### Existing canonical Hero domain

The `heroes` table and live Heroes dataset currently provide canonical identity, classification, ratings, availability, descriptive content, portrait and provenance fields.

The public Hero Companion consumes active published Hero records through `getHeroCatalogue()` and already contains an explicit Skills placeholder.

The Heroes Record Editor schema is connected to the existing editorial lifecycle and supports immutable versions, review, approval, queue-based publication, history, comparison, archive, restore and rollback.

### Existing Hero Skill persistence foundation

Supabase already contains an empty `hero_skills` table linked to `heroes` through `hero_id`.

Its existing fields are:

- `name`;
- `category` (`conquest`, `expedition`, `talent`, `exclusive_gear`);
- `skill_type`;
- `description`;
- `icon_url`;
- `display_order`;
- `slot_index`;
- `max_level`.

This table is a useful persistence foundation and will be extended rather than replaced. It currently has no connected Forge dataset contract, editorial schema, publication projection, provenance fields or public consumer.

### Existing player-owned progression

`player_heroes` stores player-specific progression, including hero level, stars, power and legacy numbered skill-level fields.

Supabase also contains an empty relational `player_hero_skills` table that links a player's Hero to a canonical `hero_skills` record and stores `skill_level`.

Those structures describe a player's ownership and progression. They are not the canonical source for skill identity, names, descriptions, categories, ordering or provenance.

### Current skill gap

There is no connected Hero Skill dataset, editor schema, live publication projection or public consumer.

Skill content must not be embedded as opaque JSON inside Hero records and must not be inferred from player progression columns.

## Architectural decision

Hero Skills will remain independent canonical records linked to Heroes.

The cross-layer dataset and editorial contract uses stable Hero slugs. The live publication projection resolves the Hero slug to the existing `heroes.id` foreign key when writing `hero_skills`.

This preserves clear ownership:

- `heroes`: canonical Hero identity and overview;
- `hero_skills`: canonical skill definitions;
- `player_hero_skills`: player-owned skill progression;
- editorial platform: draft, review, approval, publication, history and rollback;
- Hero Companion: read-only consumer of published canonical content.

No replacement table or parallel Hero-specific publishing system will be introduced.

## Canonical record model

The initial Hero Skill contract aligns with the existing persistence foundation and requires:

- stable skill ID for editorial and dataset use;
- stable Hero slug relationship;
- skill name;
- existing category vocabulary;
- optional skill type and description;
- optional icon URL;
- deterministic positive slot index;
- deterministic positive display order;
- positive maximum level;
- active state;
- provenance, verification and confidence metadata.

Slot indexes and display orders must each be unique within a Hero. Missing or uncertain facts remain nullable and must not be invented.

## Deliberate boundaries

Sprint 8.1 does not include:

- player skill-level redesign or legacy-column migration;
- Widgets, Gear, Awakening, pairings or formations;
- localisation infrastructure;
- a replacement Hero Skill table;
- a new editorial architecture;
- automatically invented skill data;
- direct public reads from editorial draft tables.

## Risks and controls

### Existing schema drift

The existing persistence table predates the canonical dataset and editorial contract.

Control: map the contract deliberately to current columns, add only required provenance and publication constraints, and avoid destructive changes.

### Ambiguous source structures

Source data may provide incomplete, differently named or differently ordered skills.

Control: normalise through a dedicated importer and reject records without a stable Hero relationship, name, category and valid ordering.

### Duplicate ordering

Two active skills for the same Hero must not share a slot index or display order.

Control: domain validation before publication and database uniqueness constraints in the persistence slice.

### Canonical and player data confusion

Numbered progression columns or `player_hero_skills` could be mistaken for skill definitions.

Control: keep canonical definitions in `hero_skills`; keep player level data in player-owned tables.

### Draft leakage

Unpublished changes must never appear in the Hero Companion.

Control: the public consumer reads only the live projection produced by the existing publication queue.

## Implementation sequence

1. Shared Hero Skill contract and domain validation aligned to the existing table.
2. Dataset registration, browser adapter and Record Editor schema.
3. Non-destructive persistence migration and live publication projection.
4. Import normalisation with honest incomplete-data handling.
5. Public Hero Companion skill service and responsive rendering.
6. Editorial, permission, concurrency, history, rollback and responsive end-to-end tests.
7. Release documentation, merge and production deployment.

## Acceptance criteria

1. An authorised editor can create or update a Hero Skill without editing raw JSON.
2. Review, approval and publication use the existing editorial services.
3. A published skill appears on the correct Hero Companion page.
4. Draft and rejected changes never appear publicly.
5. Skill ordering is deterministic and validated.
6. Missing or uncertain information is represented honestly.
7. History, comparison and rollback work for skill records.
8. A stale save is rejected without losing the editor's working copy.
9. Permissions are enforced server-side.
10. Automated checks, Vercel Functions and desktop/mobile scenarios pass.
